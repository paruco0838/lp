# 学びの記録

## 2026-08-17（その3）：同じ失敗を繰り返した ─ 判定条件に点数を使うな

### 何が起きたか

ニオイの配点を 1点 → 2点 に上げたとき、こんな判定文が残っていた。

```js
if (answers.smell && answers.smell.pts >= 2) reasons.push('ニオイがかなり気になる');
```

配点を上げた瞬間、「しばらくすると気になる」を選んだだけの人が
この条件に引っかかり、**「ニオイがかなり気になる」「完全分解をおすすめします」**
と表示されるようになっていた。マップには「すぐ臭う以上」と書いてあり、意図と違う。

### なぜ見落としたか

「配点を上げる」という作業だと思っていて、
**その点数が判定にも使われていることを確認しなかった**。
`grep smell` を一度かけていれば5秒で気づけた。

これは前日に自分で lessons.md に書いた
「点数は"程度"、選択肢の値は"事実"。判定には値を使う」という学びと
**まったく同じ内容の失敗**。dust では直したのに smell を直していなかった。

### どう直したか

`hasDirtSign()` と同じ形で、選択肢の値で判定する関数を用意した。

```js
function isStrongSmell() {
    if (!answers.smell) return false;
    return answers.smell.value === 'soon' || answers.smell.value === 'always';
}
```

### 次に活かすこと

- **配点を変える前に必ず `grep <質問キー>` を実行する。**
  その点数が判定条件に使われていないか確認してから触る
- 「pts >= 数字」という書き方を見つけたら、**その場で値ベースに直す**。
  残しておくと、次の配点変更で必ず同じ事故が起きる
- 同じ種類の修正をするときは、**似た箇所すべてを一度に洗い出す**。
  dust を直した時点で smell / efficiency も確認すべきだった
  （efficiency は `pts > 0` で症状カウントにのみ使用、こちらは意図どおり）

## 2026-08-17（その2）：平均方式では「数問だけで大きく下げる」ことは原理的にできない

### 要望

「汚れている選択肢を2つ選んだら、キレイ度が50%以下になるようにしたい」

### 計算して分かったこと

配点だけでは**実現できない**。

キレイ度は「合計点 ÷ 満点」なので、症状の配点を上げると満点も上がり、
上げた分が薄まってしまう。式で解くと、
**症状1問の配点が「残り5問の合計」と同じ重みになるまで上げないと50%に届かない**。
そこまでやると使用年数や前回清掃時期がほぼ無意味になる。

### どう解決したか

配点ではなく、すでにあった**「上限ルール」の仕組み**を使った
（「4年以上未清掃ならキレイ度は最大55%」と同じやり方）。

```js
const symp = symptomCount();
if (symp >= 3) score = Math.max(score, 62);      // キレイ度 38%以下
else if (symp >= 2) score = Math.max(score, 50); // キレイ度 50%以下
```

判定には既存の `symptomCount()`（ニオイ／黒い汚れ／効き）をそのまま使った。
結果画面の「汚れのサインが複数見られました」という警告文と同じ基準なので、
**文章と数字が必ず一致する**。

### 途中で気づいた失敗

最初は「2つ以上なら50%」の1段階だけにした。すると
**症状2つの人も3つの人も一律50%**になり、重症の人ほど軽く見える状態になった。
上限を1本にすると、そこに全員が張り付いてしまう。
→ 段階を2つに分けて解決。

### 次に活かすこと

- 「特定の条件で必ず◯%以下」という要望は、**配点ではなく上限ルールで実現する**
- 上限を入れるときは**必ず段階をつける**。1本だと重い人と軽い人が同じ値に潰れる
- 上限の判定は、**すでに画面に出している文言と同じ関数**を使う。
  別々に条件を書くと、文章と数字がズレる

### やったこと

使用頻度の選択肢を4択（夏のみ／冬のみ／夏と冬／ほぼ1年中）に変更し、
あわせて「汚れ寄りに出やすくする」ため中間の選択肢の配点を全体的に引き上げた。

### 気をつけた考え方

**最高点は変えず、中間の選択肢だけを上げた。**

キレイ度は「合計点 ÷ 満点」で出すので、最高点を上げると満点も上がり、
他の質問の重みが薄まってしまう（＝上げたつもりが効かない）。
中間だけ上げれば、満点はほぼ変わらないまま、
一般的な回答をした人の点数だけが上がる。

**両端は必ず守る。**
- 本当にキレイな人が「とてもキレイ」と出ること
- 全部最悪の人が「かなり汚れている」と出ること

この2つが崩れると診断の信用が失われるので、変更のたびに確認する。

### 検算の結果（同じ回答での変化）

| 回答パターン | 変更前 | 変更後 |
|---|---|---|
| 全部ベスト | 95% | 95%（維持） |
| きれいめ | 94% | 88%（維持） |
| ごく一般的な家庭 | 66% | **43%** |
| 症状が出ている人 | 37% | **25%** |
| 全部ワースト | 5% | 5%（維持） |

狙いどおり、真ん中の層だけが下がった。

### 次に活かすこと

- 配点を触ったら、**手計算せず実際のコードに計算させる**。
  1問ごとに四捨五入してから合計する方式なので、手計算と合わないことがある
- 選択肢の値（value）を変えたら、**その値を使っている別の場所も必ず探す**。
  今回は CONCERNS（気になったポイントの文言）が value で引かれていたため、
  'rare'/'season' を消して 'summer'/'winter' を足す必要があった
- **説明資料（shindan-map.html）も同時に直す**。
  配点表・計算式・満点・計算例の4か所すべてに数字が散っている

## 2026-08-12：診断アプリの「点数」と「判定」を混ぜると矛盾が出る

### 何が起きたか

一番キレイな回答をすべて選んだのに、結果が矛盾していた。

- キレイ度 95%
- 「とてもキレイな状態です！」
- なのに ⚠️「汚れのサインが見られました」
- そのうえ「完全分解クリーニングをおすすめします！」

### 原因

「吹き出し口の黒いカス」の質問で、**「見たことがない」に汚れ点数1点**を付けていた。
これは「見ていないので分からない＝少し不確実」という意味の1点で、妥当な設計。

問題は、その**点数をそのまま「症状があるかどうか」の判定に流用していた**こと。

```js
// 修正前：点数が1以上なら「汚れのサインあり」とみなしていた
if (answers.dust && answers.dust.pts > 0) n++;
const recommendFull = ... || (answers.dust && answers.dust.pts >= 1) || ...
```

「見たことがない」も1点なので、**確認していないだけの人が"汚れが見えている人"として扱われた**。

### どう直したか

「点数（どれくらい汚れていそうか）」と「症状の有無（実際に何か見えたか）」を分けた。

```js
// 実際に目で見えた汚れのサインだけを判定に使う
function hasDirtSign() {
    if (!answers.dust) return false;
    return answers.dust.value === 'spots' || answers.dust.value === 'debris';
}
```

点数の1点はそのまま残した（不確実性の反映としては正しいため）。

### 次に活かすこと

- **点数は「程度」、選択肢の値は「事実」**。判定には事実（value）を使い、点数は合計スコアにだけ使う
- 選択肢に点数を足したときは、その点数が**他のどの判定に波及するか**を必ず確認する
  （今回は symptomCount / recommendFull / 合計スコア の3か所に波及していた）
- 診断ロジックを変えたら、**一番キレイな回答と一番汚い回答の両端**を必ず通しで確認する。
  真ん中のケースだけ見ていると、両端の矛盾に気づけない

## 2026-08-12（続き）：合計点の平均だけでは1問の重さを表現できない

### 何が起きたか

上の修正後も、「黒い点が見える」だけを選んだ人にこう表示されていた。

- キレイ度 90% →「とてもキレイな状態です！」
- なのに「完全分解クリーニングをおすすめします！」

### なぜ配点を上げても消えなかったか

配点を 1点 → 3点 に上げても（満点も29→31に修正）、
キレイ度は **8問の合計を平均する**仕組みなので、1問だけでは10%しか動かない。

**「合計点で状態を決める」設計と、「特定の1問で判定する」設計を同じ画面に混ぜると、
配点をいくらいじっても噛み合わない。**

### どう直したか

配点ではなく、**表示ルールに上限をかけた**。

```js
function levelInfo(score) {
    const info = LEVELS.find((lv) => score >= lv.min) || LEVELS[LEVELS.length - 1];
    // 目視の汚れサインがある人には「とてもキレイ」とは言わない
    if (hasDirtSign() && info.min === 0) {
        return LEVELS.find((lv) => lv.min === 20);
    }
    return info;
}
```

キレイ度の数字（90%）はそのまま、状態フレーズだけ「おおむね良好な状態です」で止める。
色もこの関数を通しているので、フレーズと色が自動的に揃う。

### 次に活かすこと

- **数字（スコア）と言葉（フレーズ）とおすすめは、別々に決めると必ずズレる。**
  どれか1つを「正」にして、他はそこから導くか、上限・下限で縛る
- 「配点を変えれば直る」と思ったら、まず**その1問が全体の何%を動かすか**を計算する。
  平均方式なら、1問が動かせる幅は思っているよりずっと小さい
- 連携先（見積もりアプリ）の文言も一緒に見直す。
  「カビがたまっている可能性が高い」と断定していたが、キレイ度90%の人にも出るため、
  断定せず「完全分解洗浄がおすすめ」と伝える文言に変更した

## 2026-08-17（その4）：スマホでは「マウスを乗せた色」がタップ後も残り続ける

### 何が起きたか

選択肢ボタンに `:hover`（マウスを乗せたときの水色）を付けていたら、
スマホで実機確認したとき、**前の質問でタップした位置の水色が
次の質問のボタンにも残って見える**という指摘を受けた。

スマホにはマウスがないので、タップ＝「乗せっぱなし」扱いになり、
hover の色が付いたまま外れない。次の質問でボタンを同じ位置に
作り直しても、その状態を引き継いでしまう。

### どう直したか（2段構え）

1. hover の色は `@media (hover: hover)` で包み、
   **マウスがある環境だけ**に限定した（スマホでは無効になる）
2. ただし「押した手応え」は必要だったので、
   タップ時に `.is-selected` クラスで一瞬水色にし、
   **0.18秒後に次の質問へ進む**方式にした。
   あわせてロック（`dataset.locked`）で連打による二重回答も防いだ

### 学び

- PCのブラウザ確認だけでは hover の問題は絶対に見つからない。
  **タップ操作の見た目はスマホ実機で確認する**
- 「色を消す」と「手応えを消す」は別問題。ユーザーの指摘は
  「残るのが嫌」であって「光るのが嫌」ではなかった。
  直す前にどっちの意味か確認する
